# Phase 1 changelog

Every manual change made on the `locumview-ref-dev` reference VM, in the shape: what and why, exact commands, files touched, target Ansible module or Terraform setting, supported or not.

## 1. VM created with SeaBIOS instead of UEFI + Secure Boot

What and why: the reference VM was created with SeaBIOS by mistake. Target is UEFI + Secure Boot (OVMF secboot), which must be enforced in Terraform for Phase 3. The VM was not rebuilt; remaining Phase 1 work (desktop configuration) is firmware independent, so this was left as-is for now.

Target: Terraform `libvirt_domain` resource, `firmware`/`nvram` block for OVMF with Secure Boot enabled.

Supported: yes, standard libvirt/QEMU capability.

## 2. GNOME Remote Desktop TPM-sealed credentials reverted

What and why: GNOME Remote Desktop (GRD) 49.3 can seal RDP credentials to a TPM via `grdctl`. RHEL 10.2's `selinux-policy` denies the confined `gnome_remote_desktop_t` domain access to `tpm_device_t` (and denies `name_connect` to TCP 2321, the TCTI fallback path). `grdctl` runs unconfined and successfully sealed credentials that the confined `gnome-remote-desktop` daemon then could not read at startup, breaking headless RDP.

Exact commands (revert):
```
tss -d gnome-remote-desktop   # removed from tss group
grdctl rdp disable-credentials
grdctl rdp set-credentials <user> <password>   # re-set to key file, not TPM-sealed
chmod 600 ~/.config/gnome-remote-desktop/credentials.ini
```

Decision: no custom SELinux module was written to allow the access, since a custom module is not defensible under STIG. Per-start AVC denials for the TPM access attempt are expected noise until upstream fixes `selinux-policy`. This is a candidate upstream bug report against `selinux-policy`.

Target: Ansible `remote_access` role should set credentials via the key-file path, not attempt TPM sealing, until the SELinux policy is fixed upstream.

Supported: partially. TPM-sealed credentials are an upstream GRD feature but currently blocked by RHEL 10.2's shipped SELinux policy.

## 3. GNOME Remote Desktop TLS certificate

What and why: GRD generates a self-signed TLS certificate for RDP, stored at `/var/lib/gnome-remote-desktop`, key permissions 0600, SELinux type `gnome_remote_desktop_var_lib_t`.

Target: the Ansible version of this must generate a cert with proper SANs (both DNS and IP), not just a CN, since modern RDP clients reject CN-only certs.

Supported: yes, standard `openssl`/`grdctl` certificate generation.

## 4. remote_access role ordering (planned)

What and why: for the Ansible `remote_access` role, task order matters: TLS cert/key first, then credentials from vault, then enable the service, then restart, then open the firewall. Later hardening should restrict the RDP source to the guacd host only, once Phase 2 stands up Guacamole.

Target: Ansible `remote_access` role, task ordering; later a `firewalld` rich rule scoped to the guacd host IP.

Supported: yes.

## 5. Cockpit left open by default

What and why: Cockpit is open in `firewalld` by default on RHEL Workstation installs. It is not part of the LocumView access path (Guacamole/RDP only), so the `hardening` role should remove it from the allowed services unless it is explicitly needed for administration.

Target: Ansible `hardening` role, `firewalld` service removal for `cockpit`.

Supported: yes.

## 6. System UIDs/GIDs are dynamic

What and why: baseline capture (`groups.txt`) confirmed system UIDs/GIDs vary between installs. Any Ansible role or Terraform config must never hardcode a UID/GID; always resolve by name.

Supported: yes, this is just a constraint on how automation is written, not a system change.

## 7. Baseline `rpm -Va` drift

What and why: `rpm-verify.txt` in the Phase 1 evidence shows only two sources of drift from packaged state: `/etc/rhsm/rhsm.conf` (expected, from registration, managed by the `rhc` RHEL System Role) and the `pesign` NSS databases (expected, generated by the package itself). No unexpected drift found.

Supported: n/a, this is a finding, not a change.

## 8. Registration approach for automation

What and why: system registration in Ansible/Terraform must use an activation key plus org ID, never the account password, so credentials are not needed in automation and can be scoped/revoked independently.

Target: Ansible/Terraform registration step (`rhc` role or `redhat_subscription` module), activation key + org ID.

Supported: yes, this is Red Hat's documented approach for automated registration.

## 9. Gitea SSH access from the VM fixed (2026-09-29)

What and why: could not `git clone`/push over SSH to the Gitea instance at `git.lan` (192.168.4.54) from this VM, though the web UI worked. Root cause investigation (done from this VM, working on the `homelab-infra` repo which owns Gitea's k8s manifests, not this repo) found three separate problems on the k3s cluster hosting Gitea:

1. Gitea's SSH port (2222) was only exposed as a `ClusterIP` Kubernetes Service, never published outside the cluster. Fixed by adding a second Service, `gitea-ssh`, of type `LoadBalancer` (using k3s's built-in ServiceLB/klipper-lb, the same mechanism already used for Traefik), scoped to just port 2222.
2. Even with that port reachable, the connection was refused because the container's real OpenSSH daemon was still bound to port 22. It turns out the `gitea/gitea` image runs a genuine `sshd` (a separate `s6` service) alongside the Gitea web process; that `sshd`'s config is templated at container start from plain, unprefixed `SSH_PORT`/`SSH_LISTEN_PORT` environment variables, which is a different mechanism from `GITEA__server__SSH_LISTEN_PORT` (which only affects Gitea's own `app.ini` and clone-URL generation). Fixed by also setting plain `SSH_PORT=2222` and `SSH_LISTEN_PORT=2222` on the Deployment.
3. While restarting the pod to pick up the above, discovered `GITEA__security__INSTALL_LOCK` was hardcoded to `"false"` in the Deployment. The official image's `environment-to-ini` step re-applies that value into `app.ini` on every container start, so any pod restart was silently knocking the live instance back into the first-run install wizard (repo pages returned 404 while the API still answered version info). Fixed by setting it to `"true"`.

Also discovered that this Deployment's default `RollingUpdate` strategy cannot work for this workload: Gitea's leveldb-backed internal queue cannot tolerate two processes touching the same PVC at once, so a rolling update deadlocks (new pod crash-loops on a leveldb lock while the old pod is kept alive waiting for it to become ready). Changed the Deployment strategy to `Recreate`.

All four fixes are committed to `k8s/gitea.yaml` in the `homelab-infra` repo (commits `a006c4c` and `99dad99`) and applied live; not tracked in this repo since Gitea's infrastructure lives outside LocumView's scope.

On this VM: generated a per-machine SSH key (`~/.ssh/id_ed25519_gitea`), added a `gitea` Host alias in `~/.ssh/config` (port 2222), registered the public key with the `mike` Gitea account, and configured SSH commit signing (`gpg.format=ssh`, signing key = the Gitea key, `gpg.ssh.allowedSignersFile` for local verification).

Target: n/a for this repo; the fix lives entirely in `homelab-infra`'s `k8s/gitea.yaml`.

Supported: yes, standard Kubernetes Service/Deployment configuration; no workarounds or unsupported hacks.
